# Firmware architecture

Native Matter firmware for Realtek AmebaZ2 (RTL8720CF) Wi-Fi modules, such as the Tuya WBR2. Built natively on
arm64/x86_64 macOS or Linux with the Arm GNU Toolchain. (An earlier HomeKit/HAP prototype was removed; it is in
the git history.)

## Layers

Each layer may include only the layers below it.

| Layer | Path | Contents |
|---|---|---|
| L0 vendor | `vendor/` | Realtek `ameba-rtos-z2` SDK and Monocypher (Ed25519). Read-only, never edited |
| L1 platform | `platform/ambz2/` | Board config (`config/`), SDK source list (`sdk.mk`, generated by `tools/gen_sdk_mk.py`), linker script, glue for SDK symbols we don't build, the flash partition map |
| L2a pure libs | `libs/<name>/` (no `sdk` dependency) | Platform-independent C, unit-tested on the host: `tuyamcu` (protocol core), `thermo` (DP ↔ thermostat model), `tz` (POSIX TZ → local time), and the Matter protocol libs `matter-*` (below). A pure lib may depend on the `mbedtls` lib, see "Matter" |
| L2b ported libs | `libs/<name>/` | `wifi-sta`, port glue for the pure libs (`tuyamcu-port`), OTA (`ota`, `ed25519`), netlog, wdog, `httpd` (one-handler HTTP server; its request parser is pure and host-tested), `net-listen` (the TCP listener setup the socket servers share), the Matter ports (`matter-port-ambz2`, `btp-port-ambz2`) |
| L3 app | `apps/thermostat-matter` | The ET-44W thermostat: `make APP=...` (the default) |

Rules:
- A library sees only the headers of the libraries in its `_DEPS` (`build/rules.mk`), so a layering violation fails to compile.
- Libraries never include app headers.
- Pure libraries never include FreeRTOS or SDK headers.
- Our own code builds with `-Wall -Wextra -Werror`. Vendor code builds with warnings off.
- Small files, one responsibility each. `main.c` only wires modules together: create, configure, start. No multi-thousand-line files.

## Decisions

- **Flash map:** one definition (`platform/ambz2/partitions.def`) shared by the C code, the packer and OTA.
- **Setup data:** the Matter verifier, discriminator and serial are compiled in per unit (`tools/matter_setup.py` -> `units/<UNIT>/matter_unit.h`, git-ignored; never the passcode). The `factory` flash region stays reserved for a read-only per-unit record; nothing writes it yet.
- **Threads:** one Matter task owns all Matter state (see below). Each driver task (for example TuyaMCU) owns its own state and is reached through its queue. ISRs only fill stream buffers.
- **Network:** dual-stack IPv4 + IPv6 (`platform/ambz2/config/lwipopts.h` shadows the SDK's). mDNS uses lwIP's source responder. The prebuilt `lib_mdns` hardcodes the IPv4-only `struct netif` size, so it is not linked.
- **Crypto:** the SDK's mbedtls 3.1.0 with a crypto-only config. Neither the ROM nor the prebuilt SDK libraries contain mbedtls symbols.
- **OTA:** dual slot, Ed25519-signed (`libs/ed25519`: Monocypher's RFC 8032 `crypto_ed25519_check`, strict about non-canonical S). The signed header (length, serial, image hash) is checked before the idle slot is erased; placeholder/small-order keys refuse all uploads. The prebuilt bootloader picks the newer valid slot. A new image is on trial until the app's self-check confirms it; the self-check includes a known-answer test of the verifier (`ota_verifier_ok`), so an image that couldn't verify the next update rolls back instead.

## Matter

- **Build flag:** every build is a Matter build. `MATTER` stays a make variable (forced to 1, implying `BT=1`) because the Matter libs' `lib.mk` files switch on it; `matter-core` exports `-DMATTER=1` to the libs that depend on it. Output goes to `out-matter/` (use `OUT=out-matter/<unit>` per unit: make doesn't track `UNIT`).
- **Libs:** `libs/matter-<x>`, C prefix `mt_<x>_`, the shared error type `mt_err` and the byte spans `mt_span`/`mt_buf` come from the header-only `matter-core`. Layering, bottom to top:
  `core` -> `tlv`, `crypto` -> `cert`, `msg`, `btp` -> `xchg`, `pase`, `case`, `fabric` -> `im`, `dm`, `root`, `thermostat` -> `node` (wiring and the commissioning state machine) -> ports (`matter-port-ambz2`, `btp-port-ambz2`, and `tools/matter-host` on the Mac). `node` reaches hardware only through one small port interface (clock, UDP, BLE, storage, random, Wi-Fi, mDNS, credentials).
- **mbedtls as a pure dependency:** the SDK's mbedtls 3.1.0 is vendor C with no OS dependency, so pure Matter libs may list `mbedtls` in `_DEPS`. Firmware builds use `platform/ambz2/mbedtls/ambz2_mbedtls_matter_config.h` (the base config plus P-256 ECDSA/ECDH, CCM, CTR-DRBG, ASN.1; no PK/X.509/ENTROPY). Host tests compile the same sources with the same config and `MBEDTLS_HAVE_ASM` undefined, once into `out-host/mbedtls/`, via `build/hosttest.mk` (see its header for the three lines a test Makefile needs). The source list lives in `platform/ambz2/mbedtls_sources.mk`, shared by both.
- **Threading:** one Matter task owns all Matter state and blocks on a single FreeRTOS queue. The UDP RX task, BLE callbacks, TuyaMCU reports and the timer tick only post events to it. OTA and netlog start before it and run independently; Wi-Fi is started by `mtp_start` in `main()`, before the Matter task runs (see Port).
- **Storage:** Realtek DCT second instance (`dct_init2`) in the `matter` region 0x1EA000-0x1F5FFF (48 KiB, 6 modules x 4 KiB + backups), never `kv` or `ota_state`: `libs/matter-port-ambz2` wraps the DCT flash helpers and refuses writes outside `matter`. Fabric updates go through a scratch module and one index write (`store_kv.c`, host-tested with power cuts after every write).
- **Port (`libs/matter-port-ambz2`, L2b):** the Matter task (8 KiB stack, priority idle+1), the UDP socket on [::]:5540 with its RX task, mDNS records over lwIP's responder, clock, entropy, the DCT2 store, Network Commissioning over `wifi-sta` (runtime credentials, `WIFI_STA_RUNTIME`), and the boot bookkeeping: a fault counter in the store puts the node in **safe mode** after 3 watchdog resets without 5 minutes of uptime. Apps call `mtp_boot_capture()` first in `main()` and `mtp_start(&app)` instead of `wifi_sta_start()`. `mtp_start` starts Wi-Fi on the app's development network at once, in `main()`'s context, before and independent of the store and the node. The Matter task then opens the store (held 60 s after a watchdog reset, so a crash loop in DCT2 or the node still leaves an OTA window every cycle) and switches to the stored `WIFI` network if there is one, also in safe mode. DCT flash writes and erases are range-checked against the `matter` region (`src/flash_guard.h`, host-tested; a zero-length erase would wipe the whole flash in `lib_dct.a`).
- **BLE commissioning (`libs/btp-port-ambz2`, L2b; `node_btp.c` in `matter-node`):** the port owns every Realtek BLE call in its own task (GATT 0xFFF6 with C1/C2, advertising 20-60 ms for 30 s then 150-1200 ms, events drained by the Matter task); `matter-node` runs the BTP engine, the CCCD gate (no indication before C2 is subscribed), one indication in flight, the 15 s handshake and 30 s confirm timeouts. BLE runs only while a BASIC window is open (capped by `ble_window_s`); a BLE disconnect ends the BTP sessions as a transport loss and keeps the fail-safe. CommissioningComplete (always over CASE/UDP) turns BLE off before any flash write. The stack is started once: `bte_deinit` leaks ~2.4 KiB, so reopening a BLE window after it stopped reboots the unit. On this chip the heap is what is left between `.bss` and the stack, so static RAM comes straight out of the heap.
- **Device app (`apps/thermostat-matter`, L3):** `main.c` wiring (netlog, OTA, wdog, then the TuyaMCU link, the self-check and `mtp_start`); `thermo_link.c` (TuyaMCU reports -> `thermo` -> `matter-thermostat`, Matter writes -> `thermo` -> debounced DP writes; reports cross into the Matter task through a queue + `mtp_wake`); `thermo_mcu.c` (TuyaMCU glue), `clock.c` (SNTP + TZ for the MCU), `web.c` + `dp_cache.c` (settings page on port 80); `health.c` (S0 self-check -> `ota_confirm`; heap/stack lines while commissioning). Per unit: `units/<UNIT>/unit.h` (name, serial) and `units/<UNIT>/matter_unit.h` (git-ignored).
- **Tools:** `tools/size_report.py` (per-lib code/rodata/data from `app.map`, total vs the 0xE0000 slot, `--base` for deltas).

## Deliberately not built (KISS)

- No OS, UART or GPIO abstraction layer. Ports call FreeRTOS and the SDK directly.
- No event bus, no dynamic registries, no web framework: `httpd` is one task, one client at a time and one handler function; the app matches method and path itself.
- No custom KV store unless DCT fails a power-cut test.
- No delta or compressed OTA.
